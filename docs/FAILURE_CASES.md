# 失效案例与处置

## 怎么用这份文档

现场失败时，先在日志里找方括号标签（`[ALIGN]` `[MOVE]` `[BACK]` `[DOCK]` `[MEASURE]`），
再到下表定位案例。**每个案例的「判据」都是代码里真实的日志原文**，可以直接 grep。

| 日志关键词 | 案例 |
|---|---|
| `[DOCK] marker lost before blind move` | F-01 |
| `[BACK] marker not visible after move` | F-01 |
| `[ALIGN] residual stalled` / `no progress` / `not converged` | F-02 |
| `[MOVE] rejected` / `call failed` / `giving up` / `step N failed` | F-03 |
| `[MARKER] drop stale sample` | F-04 |
| `[MEASURE] only N/M samples` / `AR marker not visible` | F-05 |
| 无明显日志但初始朝向接近 180° | F-06 |

结局只有两行，直接看这个就能判断成败：

```
 Auto Charge [SUCCESS]   |   elapsed 42.3 s
 Auto Charge [FAILED]    |   elapsed 18.7 s
 phase: kFailed
```

## F-01 · 近距离 AR 码脱出视野（本项目的核心问题）

**现象**
对准阶段顺利收敛，但在「倒退到固定点」或「盲倒」阶段，AR 码从相机视野里消失。

**判据（代码原文，两处，处置不同）**

```
[BACK] marker not visible after move, continue with blind offset     ← WARN，允许继续
[DOCK] marker lost before blind move, aborting to avoid collision    ← ERROR，立即中止
```

**处置**

| 位置 | 判定 | 为什么 |
|---|---|---|
| BACK 阶段之后看不到码 | **继续**，用标定值走 | 下一步本来就是开环（`docking_distance` 是定值），没有视觉也能走 |
| DOCK 阶段**开始前**看不到码 | **中止** | 连「起点在哪」的基准都没有了，硬走等于蒙着眼倒车，可能撞桩 |

**根因**：AR 码装位低，机器人一靠近就出了相机视野。这是几何约束，不是算法精度问题 ——
**再怎么优化位姿估计，那一段也看不见。**

**设计上的应对**：把「无法闭环的最后一段」压缩成一个**已知定值**（`docking_distance = 0.35 m`），
用开环走完。这是整个方案的核心取舍：

> 不去解决「看不见还要闭环」，而是把不可闭环的部分缩到最小、并变成已知量。

**遗留风险**：`docking_distance` 是标定值。充电桩位置一变（挪了、地脚松了），这个值就错了，
而且**错了不会报错** —— 车会按旧距离倒，撞上或差一点。所以桩挪动后必须重标定。

## F-02 · 对准不收敛

**现象**：对准阶段 iterating，但残余偏差不再下降，或耗尽迭代次数。

**判据（两种，都是 ERROR）**

```
[ALIGN] residual stalled (0.08 -> 0.08), 2/2
[ALIGN] no progress, aborting instead of docking with residual error

[ALIGN] not converged after 8 iterations, aborting
```

**处置**：**中止，不进入盲倒。**

这是有意的：带着残余偏差进入开环段，等于把一个小误差放大成一次撞击。
**宁可失败退出重试，也不带病上桩。**

停滞判据是「归一化残差连续两轮改善量 < `stall_threshold`」，不是「绝对值小」——
因为收敛后期改善本来就慢，用绝对值判断会误杀。

**常见根因**
- 初始位姿偏差过大，超出一次对准的可修正范围
- 底盘速度/方向响应不一致（电池电压、地面摩擦）
- `max_align_iter` 偏小（原版 5 次常不够，现为 8）

## F-03 · 相对运动服务异常

**现象**：调用 `relative_move` 失败。

**判据（四层，从轻到重）**

```
[MOVE] rejected: <服务返回的 message>        ← WARN，服务明确拒绝（如目标不可达）
[MOVE] call failed (attempt 1/3)             ← WARN，RPC 本身失败（超时/断连）
[MOVE] step 3 failed                         ← ERROR，分段运动中第 3 步失败
[MOVE] giving up after 3 attempts            ← ERROR，重试耗尽
```

**处置**：每次调用重试 `service_retry` 次（默认 2，即最多 3 次），间隔 0.2 s。
分段运动中任一步失败，整段立即放弃，**不带着半截位移继续**。

**为什么分段失败要立即放弃**：位置已经不确定了。继续走，后面每一步都建立在一个错误的起点上。

## F-04 · AR 码数据过期

**现象**：检测到 marker，但时间戳太旧（相机卡顿、话题积压）。

**判据**

```
[MARKER] drop stale sample (0.62 s old)      ← WARN_THROTTLE 2.0s，避免刷屏
```

**处置**：丢弃该帧，不进入均值。阈值 `marker_stale_sec = 0.5 s`。

**为什么必须丢**：机器人正在移动，一个 0.6 秒前的位姿对应的是**另一个位置**。
用它做决策，等于拿旧地图找新路 —— 而且日志上看起来一切正常。

## F-05 · 采样不足 / 完全看不到

**判据**

```
[MEASURE] only 3/5 samples, result may be noisy    ← WARN，仍继续，但结果不可靠
[MEASURE] AR marker not visible (timeout 3.0 s)    ← ERROR，判定失败
```

**处置**：样本不足时继续但告警（用可得样本取均值）；完全看不到则按失败处理。

**注意**：`only 3/5` 这条 WARN 是**最容易被忽略的一条**。它不中止流程，
但意味着这次决策的位姿估计噪声更大 —— 事后分析成功率时，要把带这条告警的轮次单独看。

## F-06 · 初始朝向接近 180° 时角度平均失真（已知限制，未处置）

**现象**：无日志可判 —— **这正是问题所在**。

**根因**：对准阶段对偏航角取多帧**算术平均**。这个做法只在角度接近 0 时成立。
若初始朝向偏差接近 ±180°，各帧角度可能落在 +179° 和 −179°，算术平均得到 ≈0°，
而真实答案是 180°。**误差 180 度。**

**当前应对**：靠人工摆放保证初始朝向偏差小 —— 这是**流程上的规避，不是代码上的修复**。

**改进方向**（未实现，仅记录）

用圆周均值代替算术平均：

```
yaw_mean = atan2( Σ sin(yaw_i), Σ cos(yaw_i) )
```

单位向量求和的辐角天然处理跨界，不需要额外分支。

**为什么先不改**：这会改变对准阶段的核心数值行为，必须有实机数据做前后对照才能确认不引入新问题。
在没有对照实验之前改它，属于「看起来更对，但不知道是否更好」。

## 共性：这类系统的错误都不在「算错」

把五个案例放在一起看，会发现它们有一个共同点：

| 案例 | 真正的风险 |
|---|---|
| F-01 | 不是精度不够，是**物理上看不见** |
| F-02 | 不是收敛慢，是**带病继续更危险** |
| F-03 | 不是调用失败，是**失败后位置不确定** |
| F-04 | 不是数据错，是**数据对但已过期** |
| F-06 | 不是算法错，是**假设在边界外不成立** |

**它们的共同形态是：系统不报错，仍然在动，但依据是错的。**

所以这份文档的判据一律写「日志原文 + 为什么这样处置」，而不是「怎么修」——
**先能准确判断当前处在哪种失效，才谈得上修。**
